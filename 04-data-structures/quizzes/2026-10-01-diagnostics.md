# Диагностика: структуры данных — 2026-10-01

## Вопрос 1. Стек: правильная скобочная последовательность
Задача: [04-data-structures/tasks/01-valid-brackets](../tasks/01-valid-brackets/README.md) (LeetCode 20).

**Ход решения ученика:**
- Сначала предложил объект с ключами 0, 1, 2… («важен порядок»). После наводящих вопросов
  («с какой открытой сравнивать `}`? что делать с парой после совпадения?») сам пришёл к алгоритму:
  кладём открывающие, на закрывающей сравниваем с последней, при совпадении удаляем, в конце массив пуст.
- Код написал сам, рабочий, 15/16 тестов с первого раза: пустая строка считалась невалидной (`arr.length !== 0`).
- После ревью сделал рефакторинг: убрал `split`, `newArr` → `stack`, `if/else` вместо двух `if`,
  один объект пар вместо трёх списков, убран мёртвый хелпер, добавлена проверка нечётной длины. 16/16.

**Теория:**
| Вопрос | Ответ ученика | Разбор |
|---|---|---|
| Какая структура и почему | Стек, LIFO | Название верно, «почему» не объяснил: скобки вложены → закрывается последняя открытая; вершина стека = скобка, которую нужно закрыть следующей |
| Сложность по времени | Назвал O(1) у push/pop/peek | Спрашивали про весь алгоритм: n × O(1) = O(n). С подсказкой верно объяснил, почему `includes` по 3 ключам — O(1) |
| Память, худший случай | O(n); худший — `"(((())))"` | O(n) верно; худший — `"(((((((("` (стек = n), а не n/2 |
| Ранний выход | Закрывающая при пустом стеке | Верно для цикла; до цикла не назвал: нечётная длина → `false` (дал ответ) |

**Замечания по коду (повторяются):** `if (cond) return true; return false` вместо `return cond`;
придумал своё правило для edge case вместо того, чтобы спросить интервьюера.

**Оценка: стек — 2 (близко к 3).** Рабочий код пишет сам (прогресс относительно алгоритмов), но структуру выбрал
через наводящие вопросы, «почему» не обосновал, сложность собирал с подсказками.
Для 3: следующую задачу на стек — без подсказок, со сложностью вслух.

## Вопрос 2. Связный список (2026-10-03)
| Вопрос | Ответ ученика | Разбор |
|---|---|---|
| Что такое связный список, отличие от массива, узел в JS | У каждого элемента ссылки на следующий и предыдущий; у массива известны адреса | Описал только двусвязный (классика — односвязный, `{ value, next }` + `head`). Не назвал главное: массив — непрерывный блок, адрес = начало + i × размер → O(1); узлы списка разбросаны. Узел объектом не описал |
| Доступ по индексу | Массив O(1), список O(n) — проход по ссылкам | ✅ |
| Вставка в начало | Массив O(n) — сдвиг; список O(1) | ✅ Механизм описал для двусвязного; для односвязного `node.next = head; head = node` |
| Вставка в середину при известном узле | Массив O(n), список O(1); спросил, что значит «ссылка на узел уже есть» | ✅ Оценки верны. Ловушка: вставка по индексу i в списке — O(n) из-за поиска узла; O(1) только при узле на руках |
| Где встречается во фронтенде | Хуки — не знаю; DOM — дерево со ссылками на родителя и детей | DOM: дети связаны как двусвязный список (`nextSibling`/`previousSibling`, `firstChild`/`lastChild`). Хуки — односвязный список на fiber → правило хуков (порядок вызовов) |
| Почему в JS почти всегда массив | Единый блок памяти лучше; частый доступ по индексу; список оправдан при частых вставках в начало/середину | ⚠️ Направление верное, но без ключевых причин: кеш процессора (локальность данных — соседние элементы читаются пачкой), накладные расходы на объект-узел и ссылки, оптимизации V8 для массивов, богатый API; push/pop в конец массива — O(1); вставка «в середину» всё равно требует поиска O(n). Список оправдан для очередей (`shift` у массива O(n)), LRU-кеша, undo/redo |

**Оценка: связные списки — 2.** Сложности операций знает и обосновывает, но не объяснил устройство памяти массива,
описал только двусвязный вариант, не знал о хуках как списке, причины выбора массива на практике назвал поверхностно.

## Итог диагностики
**Раздел: 2 (предв.).** Стек 2, связные списки 2. Сильная сторона — сложности операций знает и рассуждает о trade-off.
